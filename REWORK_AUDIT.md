# Pickle Rush — Rework Audit (Phase 1)

**Branch:** `rework/pickle-rush` · **Audited:** 2026-11-03 · **Scope:** read-only — no application code was changed to produce this report.

## Executive summary

Pickle Rush's foundations are more solid than they look at first glance: auth boundaries (`requireAuth`/`requireAdmin`), the booking flow's double-booking guard, and the PayHere signature verification are all correctly implemented and properly scoped. TypeScript and lint are clean. Responsive layout and accessibility structure (heading order, labeled controls) are genuinely good.

The real problem is **trust, not plumbing**: multiple customer-facing promises — a 4-hour cancellation window, no-show forfeiture, group/membership discounts, "30+ Active Members," three named staff, a Terms of Service link — are not backed by any code or data. Layered on top of that, one endpoint can unconditionally and irreversibly delete every customer and booking with no server-side confirmation, and the admin Settings page doesn't actually save anything. None of these are subtle — they're the kind of thing that causes a real incident or a real complaint the first week after launch.

**19 findings total: 6 Critical, 6 High, 8 Medium/Low**, plus a zero-test-coverage risk ranking. Full list below, worst first.

**Update, same day:** C1 (the unconditional reset endpoint) has been fixed — removed outright, at your request, ahead of Phase 2. See C1 below for what changed and how it was verified.

## Findings — Critical

### C1. ~~`/api/admin/reset` unconditionally deletes all bookings and all customer accounts, with no server-side confirmation~~ — **FIXED**
**Status:** Fixed on `rework/pickle-rush` ahead of Phase 2, at your request. `app/api/admin/reset/route.ts` and `components/AdminResetPanel.tsx` were deleted outright (the route's own comment already said to remove it before launch); the dashboard's `<AdminResetPanel onReset={refresh} />` usage and its now-dead `refresh` callback were removed from `components/AdminDashboardContent.tsx`. Verified: `npx tsc --noEmit` clean, `npm run lint` unchanged (same 6 pre-existing warnings, nothing new), `npm run build` succeeds with `/api/admin/reset` gone from the route list (33 routes, down from 34).
**File (as found):** `app/api/admin/reset/route.ts:18-47`, `components/AdminResetPanel.tsx`
**What goes wrong:** `db.delete(bookings).returning(...)` has **no `WHERE` clause at all** — it deletes every row in the `bookings` table, not just "test" bookings, plus every Supabase Auth account and `users` row with `role = "customer"`. The only gate is `requireAdmin` (a valid staff session). The UI's "type RESET to confirm" dialog (`components/AdminResetPanel.tsx:85-116`) is **client-side only** — the API itself accepts the POST with zero body/confirmation check, so anything holding a valid admin bearer token (a curl request, a compromised admin session, a browser extension with devtools access) can wipe the database in one call.
**Plain English:** This is a loaded gun pointed at your own database. The code comment literally says *"Remove this route... before launch"* — it was built as a dev convenience and never removed. One mistaken click, leaked admin token, or automated test hitting the wrong environment permanently destroys every real customer and booking.
**Note:** I never called this route, per your safety rules.

### C2. Admin "Settings" page doesn't save anything — `handleSave` never calls the API
**File:** `app/admin/(dashboard)/settings/page.tsx:34-38`
```ts
const handleSave = () => {
  setSaved(true);
  setTimeout(() => setSaved(false), 3000);
  // Call API to save settings
};
```
**What goes wrong:** Clicking "Save Settings" shows a green "Saved" confirmation, but the function never fetches `/api/admin/settings` (which does exist and does work — see `app/api/admin/settings/route.ts`). Nothing an admin types here is persisted.
**Plain English:** Staff will believe they've changed the cancellation window, default payment mode, or max booking-advance-days. They haven't. This is the kind of bug that causes a real operational incident the first time someone relies on it.

### C3. The "Free cancellation up to 4 hours before" policy is never enforced — it's marketing copy over dead code
**Files:** `lib/utils.ts:142-151` (the function that implements this check), `app/api/bookings/[id]/route.ts:151-200` (the cancel endpoint, which never calls it), `app/(customer)/book/page.tsx` (the perk copy)
**What goes wrong:** `canCancelBooking(bookingDateTime, cancellationHours)` exists and correctly implements the stated policy — but it has **zero call sites anywhere in the codebase** (confirmed by grep across every `.ts`/`.tsx` file). `DELETE /api/bookings/[id]` cancels a confirmed booking at any time, with no check against how soon the slot is.
**Plain English:** A customer can cancel one minute before — or even after — their court time starts, with no restriction, while the site tells them cancellation is free "up to 4 hours before." Either the policy should be enforced, or the copy should stop promising it.

### C4. The "Booking Policy" box on My Bookings makes four specific promises with zero code backing
**File:** `app/(customer)/my-bookings/page.tsx:11-15`
**What goes wrong:** Static copy (not data-driven) tells every customer: "Free cancellation up to 4 hours before" (dead code — see C3), "No-show forfeits the full amount (non-refundable)" (no no-show status, cron job, or forfeiture logic exists anywhere), "Group discount available for 3+ consecutive bookings" (`calculateBookingAmount` is a flat per-slot sum, no discount logic exists), "Membership discounts applied automatically at checkout" (no membership-tier concept exists anywhere in the schema).
**Plain English:** This card tells paying customers about a cancellation deadline, a no-show penalty, and two kinds of discounts that are pure fiction. A customer who expects a discount, or who assumes a no-show has real financial consequences (when they can actually cancel free with zero notice, per C3), is being actively misled. Either build these, or delete the card — it should not ship as-is.

### C5. Signup requires agreeing to a Terms of Service that doesn't exist
**File:** `app/(auth)/signup/page.tsx` (checkbox link target is `href="#"`)
**What goes wrong:** Users must check "I agree to the Terms of Service" to create an account. The link is a no-op anchor (`#`) — there is no `/terms` or `/privacy` route anywhere in the app.
**Plain English:** This is a real compliance and trust gap, not a cosmetic one — people are asked to legally agree to terms that were never written. Notably, the project's own `UI-CONFIG.md` "avoid the generic AI look" checklist explicitly lists "no TOS" and "no privacy policy" as mistakes to avoid — this is that exact mistake, live on the signup form.

### C6. The homepage "Our Team" section names three people who don't appear to be real
**File:** `app/(public)/page.tsx` ("Our Team" section — Roshan Silva, Anita Perera, Chathura Jayawardena)
**What goes wrong:** Per the real database (2 customer accounts, 2 admin/staff accounts — see Business-Fact Verification below), nothing ties these three named individuals to an actual account or role.
**Plain English:** This is a stronger version of the "30+ Active Members" problem — it's not a vague stat, it's specific invented identities (with implied roles) presented as real people working at a real business. Needs to become real staff info, or be removed, before launch.

## Findings — High

### H1. Guests who book without an account can never cancel or reschedule their own booking
**Files:** `app/api/bookings/[id]/route.ts:25,65,156` (all three methods call `requireAuth`), `lib/server-auth.ts:39-47`
**What goes wrong:** `GET`/`PATCH`/`DELETE` on a booking all require a real Supabase session. A guest booking (`userId: null`, identified only by name/phone/email) has no session by definition — there is no code path that lets a guest manage their own booking.
**Plain English:** Combined with C3's marketing copy, the site promises every customer free cancellation, but a guest has no way to exercise it themselves — they'd have to call the venue and hope staff can find their booking. This is a real product gap, not just a bug.

### H2. No rate limiting on `/api/auth/login` (shared by customer and admin login)
**Files:** `app/api/auth/login/route.ts`, `components/AdminLoginForm.tsx:23-27`
**What goes wrong:** Nothing in the route or anywhere upstream throttles repeated login attempts for the same email. Admin login (`AdminLoginForm.tsx`) posts to the exact same endpoint as customer login — no separate hardening for the higher-value account.
**Plain English:** An attacker can attempt unlimited password guesses against any account, and the highest-value target is the admin account, which is the only thing standing between an outsider and C1's reset endpoint plus every customer's PII.

### H3. The `pricing` and `settings` database tables are fully built, admin-editable, and completely ignored by the app
**Files:** `lib/utils.ts:95-100` (`calculateBookingAmount`, hardcoded), `lib/constants.ts:20-28` (`SAMPLE_PRICING`, `CANCELLATION_POLICY_HOURS`), zero matches for `from(settings)` / `from(pricing)` anywhere under `app/` outside the settings CRUD route itself
**What goes wrong:** I confirmed via a read-only query that the `pricing` table has 2 real rows (off-peak 06:00-17:00 @ LKR 1,500, peak 17:00-22:00 @ LKR 2,500 — see Business-Fact section) and the `settings` table has 3 real keys (`cancellation_policy_hours`, `default_payment_mode`, `max_booking_advance_days`). None of this is ever read by the booking flow — pricing and the cancellation window are hardcoded constants in `lib/constants.ts` instead.
**Plain English:** Right now the hardcoded prices happen to match the DB's real pricing rows, so nothing is visibly broken today — but the moment anyone (now via direct SQL, or later via a working settings page) changes the DB values expecting the site to reflect them, it won't. This is a trap for future maintenance, compounded by C2.

### H4. "30+ Active Members" is a false claim — confirmed against the real database
**File:** `app/(public)/page.tsx:55`
**What I checked:** read-only `SELECT role, count(*) FROM users GROUP BY role` → **2** real customer accounts exist, not 30+.
**Plain English:** This number needs to come from you or be removed/replaced with something true before launch. Flagging per your instruction not to invent business facts — see the Business-Fact Verification section below for what I *could* confirm as true.

### H5. Admin revenue reporting is measurably wrong
**File:** `app/api/admin/reports/route.ts:31-33, 97, 99-103`
**What goes wrong:** Three separate bugs in one route: (1) `totalRevenue` sums `amountLkr` across every booking in the date range with no `status`/`paymentStatus` filter — cancelled and never-paid bookings count as revenue. (2) The online-vs-pay-at-venue split is decided by `b.notes?.includes("online")`, but `app/api/bookings/route.ts` writes *every* self-service booking's notes as `` `Booked via online system - ${paymentMode}` `` regardless of which payment mode was actually chosen — so a "Pay at Venue" booking's notes still contain the substring "online" and gets miscounted. In practice this currently misclassifies nearly all real self-service bookings. (3) `peakPaymentDay: "Saturday", // TODO: Calculate from data` (line 97) is a hardcoded fake value, returned to the UI indistinguishably from the genuinely-computed numbers around it.
**Plain English:** Anyone — you, staff, a future hire — making a decision off this report's revenue or payment-mix numbers is working from wrong data, with no visual indication that anything's off.

## Findings — Medium

### M1. PayHere payment notify doesn't cross-check the notified amount against the expected charge; no customer-facing retry after a failed/cancelled payment
**Files:** `app/api/payments/notify/route.ts:44-61`, `components/MyBookingsList.tsx` (no retry action for `pending_payment` bookings)
**What goes wrong:** The notify handler correctly verifies PayHere's MD5 signature before trusting anything (good) and correctly ignores any payload that doesn't match that signature — so this isn't exploitable without the merchant secret. But it never compares `payhere_amount` against the `payments.amountLkr` row it's about to mark paid, which is a standard defense-in-depth check for payment webhooks. Separately: when a payment fails or is cancelled, the booking is left at `status: "pending_payment"` forever — `MyBookingsList.tsx`'s action buttons only offer Reschedule/Cancel for upcoming bookings, never "Retry Payment."
**Plain English:** A customer whose card is declined has no way to complete their booking except starting over, and their stalled booking just sits there with no resolution path.

### M2. A real double-booking race surfaces as a generic error instead of the existing friendly one
**Files:** `app/api/bookings/route.ts:136-142`, `app/api/bookings/[id]/route.ts:142-148`
**What goes wrong:** The DB's unique index on `(courtId, bookingDate, startTime)` (`lib/db/schema.ts`) does correctly prevent a true double-booking even under a race (two people submitting the same slot at once) — that part works. But the generic `catch` blocks in both the booking-creation and reschedule routes don't distinguish a unique-constraint violation from any other failure, so the loser of the race sees "Failed to create booking" / "Failed to update booking" (500) instead of the existing, friendlier "Slot already booked" (409) the pre-check path already returns for the common case.
**Plain English:** Nothing breaks, but a customer who loses a genuine race for a slot gets a scarier, less actionable error message than necessary.

### M3. Signup allows email enumeration and isn't transactional
**File:** `app/api/auth/signup/route.ts:25-59`
**What goes wrong:** A distinct `"Email already registered"` 409 lets anyone probe which emails have accounts (no rate limiting here either). Separately, Supabase Auth user creation and the `users` table insert aren't wrapped in a transaction — if the Auth call succeeds but the DB insert fails, you're left with an orphaned Auth account with no matching `users` row, which `requireAdmin`/`checkOwnerOrAdmin` implicitly assume always exists.
**Plain English:** Low likelihood, but when it happens it produces a login that "works" at the auth layer but breaks everywhere the app expects a full user profile.

### M4. "Today" is computed in the visitor's browser timezone, not Asia/Colombo
**File:** `components/ui/DatePicker.tsx:35-40`
```ts
function toYMD(d: Date): string {
  const y = d.getFullYear();   // browser-local, not Asia/Colombo
  ...
```
**What goes wrong:** `lib/utils.ts`'s `formatDate`/`getDayName` correctly pass `timeZone: TIMEZONE` (Asia/Colombo) to `Intl.DateTimeFormat`. `DatePicker.toYMD`, used to compute the booking form's min/max selectable dates, does not — it uses the browser's local calendar date.
**Plain English:** For any visitor whose device isn't set to Sri Lanka time (an overseas visitor planning a trip, anyone testing from abroad, or just a wrong device clock), the selectable date range can be off by a day, especially right around midnight in either timezone.

### M5. "Weekend rate" is defined in code and copy but never actually used — confirmed against the real `pricing` table too
**Files:** `lib/constants.ts:20-25`, `lib/utils.ts:95-100`
**What goes wrong:** `SAMPLE_PRICING.weekendRate` exists and is documented as "All day on weekends," but `calculateBookingAmount` only ever checks `hour < 17`, never day-of-week. The real `pricing` table rows I read both have `day_of_week: null` ("all days") — so there's no weekend-specific pricing configured anywhere, DB included, despite the naming implying there should be.
**Plain English:** If weekend pricing is meant to differ from weekday pricing, it currently doesn't, anywhere in the system.

## Findings — Low / Informational

### L1. Admin walk-in bookings trust a client-supplied price
**File:** `app/api/admin/bookings/route.ts:106-119`
The customer-facing booking route correctly recomputes price server-side (`calculateBookingAmount`) specifically to prevent price tampering. The admin walk-in route accepts `amountLkr` straight from the request body instead. Low risk since it's staff-only, but inconsistent with the rest of the app's stated rule.

### L2. Session tokens live in `localStorage`, not an httpOnly cookie
Project-wide, deliberate architecture choice (no cookie/session middleware, per the project's own docs) — not a bug, but worth naming as a trade-off: any future XSS elsewhere in the app would be able to read a session token, including an admin's.

### L3. PayHere signature check uses plain `===`, not constant-time comparison
`lib/payhere.ts:53`. PayHere's documented scheme is MD5-based and this is their mandated contract — not something we can meaningfully harden further. Informational only.

### L4. `DEVELOPER_GUIDE.md` is substantially stale
Describes a 4-step booking wizard that no longer exists, calls the (now-real) availability check "hardcoded demo data," and claims *"no role/session check on any API route"* — which this audit's own findings (H1-H4, the `requireAdmin`/`requireAuth` coverage confirmed clean across every route) show is no longer true. It also still references `mobile/app/payhere-checkout.tsx` (deleted this session) and the pre-`(dashboard)`-route-group admin paths (`app/admin/layout.tsx`, `app/admin/settings/page.tsx`, `app/admin/dashboard/page.tsx` — real paths are now under `app/admin/(dashboard)/...`). Of its specific claims: the settings one ("handleSave doesn't call the API") is **still true** (see C2); the dashboard one ("stats are literal numbers in JSX") is **no longer true** — `AdminDashboardContent.tsx` genuinely fetches from the admin API routes now (though it then inherits H5's correctness bugs). Separately, `README.md` claims customer auth is "Phone number + email authentication (OTP-based for MVP)," while the actual implementation (confirmed by direct code read) is plain Supabase email/password with no OTP anywhere — another stale/contradicted claim, caught by the `/graphify` pass as an AMBIGUOUS cross-document edge. Risk: a future contributor or AI agent trusting any of these docs gets actively misled about the current security posture or auth flow.

### L5. `lib/hooks.ts` is entirely dead code
Five custom hooks (`useForm`, `useAsync`, `useDebounce`, `useLocalStorage`, `usePagination`) are defined and exported but never imported anywhere in the app (confirmed by grep for `from "@/lib/hooks"` — zero matches). Found via the `/graphify` community-clustering pass, which isolated them as their own disconnected cluster.

### L6. A few more real, lower-stakes findings from the parallel audits
- **Signup/login unnecessarily use the Supabase service-role client for `signInWithPassword`** (`app/api/auth/login/route.ts:4-7`) — the anon-key client `lib/server-auth.ts` already uses is sufficient for this call; not an active leak, but unnecessary privilege for defense-in-depth.
- **No phone/email format validation on signup** (`app/api/auth/signup/route.ts:16-23`) — `isValidPhoneNumber` exists in `lib/utils.ts` but is dead code, never called.
- **`lib/db/seed.ts` is out of sync with the live schema** — seeds one court named "Pickle Rush" (conflating venue name with court name) where the real DB has three courts named "Court 1/2/3" via a separate script; running `npm run db:seed` today would overwrite the real court setup. Seeded users also bypass Supabase Auth and can't actually log in (a known, still-true gap).
- **N+1 query in `/api/admin/customers`** (`route.ts:35-48`) — one `SELECT` per customer inside `Promise.all`, instead of the `inArray` + `Map` pattern the sibling bookings route already uses correctly.
- **"Last booking" date isn't reliably the last booking** (`app/api/admin/customers/route.ts:45`) — takes the last array element with no `.orderBy()`, and Postgres doesn't guarantee row order without one.
- **`window.location.href` full-page navigation after login/signup** (`LoginForm.tsx:50`, `SignupForm.tsx:61`, `AdminLoginForm.tsx:61`) — forces a full bundle reload instead of a client-side route change; flagged by ESLint, minor perceived-performance cost.
- **6 trivial ESLint warnings total** (the above ×3 files, plus 3 unused `catch` variables) — `npx tsc --noEmit` is fully clean.

### Zero test coverage — risk ranking
No `*.test.ts`, `*.spec.ts`, `__tests__/`, or test-runner config (`playwright.config.*`, `jest.config.*`, `vitest.config.*`) exists anywhere in the repo. Ranked by what would break silently and matter most:

1. **Double-booking race** (`app/api/bookings/route.ts`, SELECT-then-INSERT, backed only by the DB's `bookingUniqueIdx` unique constraint) — a future refactor that accidentally drops the constraint-violation handling (or the constraint itself, during a schema change) would only be caught by a customer actually double-booking a slot in production.
2. **`verifyNotifySignature`** (`lib/payhere.ts`) — the only thing standing between "a public, unauthenticated webhook" and "anyone can mark any booking as paid." A single off-by-one in the concatenation order, or a missed `.toUpperCase()`, would silently accept forged payment confirmations or silently reject every real one (money collected, booking never confirmed). Either failure mode is severe and neither would be caught by anything short of a real transaction.
3. **`requireAdmin`/`checkOwnerOrAdmin`** (`lib/server-auth.ts`, `app/api/bookings/[id]/route.ts`) — the entire customer/admin data boundary rests on these two functions. No test pins their behavior, so a refactor could flip a condition and let a customer read/cancel another customer's booking with nothing catching it until someone notices.
4. **Cancellation/reschedule double-booking on `PATCH`** (`app/api/bookings/[id]/route.ts`) — same unique-constraint-dependent safety net as #1, but on the update path, completely untested.

Given the DB is being treated as production for this audit, none of the above were exercised live — this is a static-analysis-only assessment of what has no safety net, not a report of an observed failure.
